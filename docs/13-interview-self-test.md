## 第二轮：技术栈连环问｜常被问

### 请求路径

先说请求路径。**一句话层。**

MentorFlow 是 Windows 桌面程序，PySide6 建立桌面窗口，Qt WebEngine 显示 React 页面；页面经 QWebChannel（网页与本机程序之间传递请求的桥）把操作交给 Python 本机程序。QWebChannel 把带编号、方法名和参数的请求交给宿主处理器。**三句话层。**

像前台把请求交给本机老师处理；实际传递的是受控消息，不是纸单。**深一层。**

**你可以这样跟面试官说：**“PySide6 和 Qt WebEngine 承载 React 页面，页面通过 QWebChannel 把操作交给本机 Python。Python 处理学习业务，再把结果交回界面；桥传递带方法和参数的请求，不让网页直接改数据库。”

#### 常被问｜前端和 Python 怎样接力处理一次操作？

<details>
<summary role="complementary">参考要点（先作答，再展开）</summary>

- React 负责显示交互，Python 宿主处理学习业务与本地状态。
- QWebChannel 把带编号、方法名和参数的请求交给宿主处理器。
- 宿主返回响应或事件，页面据此更新画面。
</details>
### 三类数据

再分三类数据。**一句话层。**

本机 SQLite 保存学习数据，服务器 PostgreSQL 保存服务器数据；同步传递相关记录，不是每次点击都直接写服务器库。课程库保存计划、资料文字块、题库、作答和账本事件。客户端把抽取后的文字块分批上传给 Java 服务。客户端用自己的 Key 直连生成模型；项目配置了 DeepSeek 提供商及其默认模型，Key 从本机操作系统的凭据库读取。**三句话层。**

事务控制一组写入的提交或撤回，认证和行级策略各管不同边界；这个账本比喻不代表 SQLite 文件就是服务器数据库。**深一层。**

**你可以这样跟面试官说：**“SQLite 管本机课程，PostgreSQL 管服务器数据，客户端用用户自己的 Key 直连模型。同步是独立记录链路；事务保证一组写入一起完成，认证通过也不代表可以读所有账号数据。”

#### 偶尔问｜为什么不把课程数据、服务器数据和模型请求放在一起？

<details>
<summary role="complementary">参考要点（先作答，再展开）</summary>

- 本机 SQLite 保存学习数据，服务器 PostgreSQL 保存服务器数据；同步传递相关记录，不是每次点击都直接写服务器库。
- 客户端把抽取后的文字块分批上传给 Java 服务。
- 客户端用自己的 Key 直连生成模型；项目配置了 DeepSeek 提供商及其默认模型，Key 从本机操作系统的凭据库读取。
</details>

### 资料到回答

再从资料找答案。**一句话层。**

本机抽文，文字分批入库。用户选中文件后，客户端在本机抽取文字，切成带页码或章节信息的文本块，再把这些文字块分批送到 Java 服务；原始文件不上传。在 MentorFlow 里，客户端把问题送到 Java 服务找资料，再由客户端把找回的段落连同问题交给模型网关；Java 服务负责查找，不负责生成最终回答。这能让模型回答时多一份可检查的依据，也可能减少凭空发挥；但“给了资料”不等于“答对了”。检索到的段落可能不够，模型也可能读错或答偏。**三句话层。**

像跑腿员找出相关讲义交给老师；找到相似段落仍要核对原文。**深一层。**

**你可以这样跟面试官说：**“客户端本机抽取文字，上传文字分块而不是原文件；Java 检索相关片段，客户端再调用模型生成回答。RAG 增加回答依据但不保证正确，引用要回到原文核对。”

</details>
## 第四轮：Java 后端连环问｜常被问

### 迁移边界

先讲迁移边界。**一句话层。**

用户求职方向是 Java + AI，因此服务器适合 Java 的业务按块迁移，客户端不动，模型请求仍从客户端直连。Java 与 Python 遵守同一 HTTP 契约，服务器业务已于 2026 年 10 月 16 日整组切到 Java 并保留回退；提示词和客户端编排继续用 Python。注册、找回等发邮件流程尚未在线上真实走过。**三句话层。**

Keycloak 验证身份，Spring Security 认证进入接口的凭证，业务还要检查账号和工作区成员。**深一层。**

**你可以这样跟面试官说：**“用户的求职方向是 Java + AI，所以把适合 Java 的服务器业务分块迁移，客户端和模型调用保留原边界。两端遵守同一 HTTP 契约，正式切换时保留回退；身份验证和业务授权仍是不同检查。”

#### 常被问｜为什么迁移服务器业务，却保留 Python 客户端和 AI 编排？

<details>
<summary role="complementary">参考要点（先作答，再展开）</summary>

- 用户求职方向是 Java + AI，因此服务器适合 Java 的业务按块迁移，客户端不动，模型请求仍从客户端直连。
- 客户端不改，Java 与 Python 遵守同一 HTTP 契约。
- 提示词和客户端编排继续用 Python。
</details>
### 登录与权限

再看登录边界。**一句话层。**

身份令牌由资源服务器核对签名和声明；桌面登录服务还会检查它对应的本机进程会话是否仍有效。身份有效后，业务仍要检查账号是否开放、用户是否属于请求的组织或工作区；登录成功不代表有权读取任意空间。**三句话层。**

PostgreSQL 和 Keycloak 是两个独立系统，无法由一个 JDBC 事务同时提交或回滚；检查点允许失败后继续原操作。**深一层。**

**你可以这样跟面试官说：**“Keycloak 提供身份凭据，Spring Security 验证进入接口的令牌；业务再检查账号状态和工作区权限。注销还要跨 PostgreSQL 和 Keycloak 分步执行，失败可从检查点继续。”

#### 常被问｜令牌有效是否代表可以读取所有账号数据？

<details>
<summary role="complementary">参考要点（先作答，再展开）</summary>

- 原生 access 有效期为 300 秒，刷新后会轮换 refresh；数据库保存刷新令牌摘要和会话主体，不保存刷新令牌明文。
- 验证令牌后，服务还要检查账号是否开放、用户是否属于请求的组织或工作区；令牌有效本身不代表有权读取任意空间。
- PostgreSQL 和 Keycloak 是两个独立系统，无法由一个 JDBC 事务同时提交或回滚。
</details>
### Java 数据库迁移

再看库表权限。**一句话层。**

Alembic 迁移仍由专门迁移角色执行，Java 不在启动时自动建表。数据库用行级安全（RLS）按事务绑定的账号/租户范围限制行访问。BUG-107 暴露过线上权限与测试夹具不一致：迁移角色对 `account_closure` 只有 `USAGE`、没有 `CREATE`，所以替换注销函数时报权限错误；修复是在替换函数时临时 `SET LOCAL ROLE mentorflow_closure`，没有给迁移角色额外授权。**三句话层。**

迁移角色能切换到函数属主角色，但不自动继承它的 CREATE 权限，也就是创建数据库对象的权限。**深一层。**

**你可以这样跟面试官说：**“Java 启动时不自动建表，Alembic 仍用专门角色迁移；业务请求按事务范围交给 RLS 限行。曾因线上迁移角色缺 CREATE 失败，我们临时切换已有函数属主角色，不扩大授权，并检查升级结果。”

#### 常被问｜Java 启动、迁移角色和 RLS 各负责什么？

<details>
<summary role="complementary">参考要点（先作答，再展开）</summary>

- Alembic 迁移仍由专门迁移角色执行，Java 不在启动时自动建表。
- 数据库用行级安全（RLS）按事务绑定的账号/租户范围限制行访问。
- 修复是在替换函数时临时 `SET LOCAL ROLE mentorflow_closure`，没有给迁移角色额外授权。
</details>
### 同步顺序

先讲同步顺序。**一句话层。**

客户端先带着上次保存的游标读取变更；服务器按游标分页返回记录，客户端把远端记录交给本地存储合并，再保存新的游标。接着客户端读取本机待上传队列，优先把记录分批提交；较新的服务器支持批量接口，旧服务返回 404 或 405 时，客户端会退回逐条接口。**三句话层。**

如果两台都改同一个字段，就比较字段更新时间；本机和远端的版本信息包含时间与设备编号，时间相同再按设备编号作稳定排序，并提示用户哪份计划的哪些字段各自保留。两台电脑时钟差很大时，按时间判断谁后改可能出错。**深一层。**

**你可以这样跟面试官说：**“一轮先拉服务器变更，再推本机待上传记录。客户端按字段合并，若同一字段两边都改，就按时间和设备编号排序并提示用户；时钟差太大时，先后判断可能不准。”

#### 常被问｜两台设备离线修改时，同步怎样避免整条覆盖？

<details>
<summary role="complementary">参考要点（先作答，再展开）</summary>

- 客户端先带着上次保存的游标读取变更；服务器按游标分页返回记录，客户端把远端记录交给本地存储合并，再保存新的游标。
- 接着客户端读取本机待上传队列，优先把记录分批提交；较新的服务器支持批量接口，旧服务返回 404 或 405 时，客户端会退回逐条接口。
- 如果两台都改同一个字段，就比较字段更新时间；本机和远端的版本信息包含时间与设备编号，时间相同再按设备编号作稳定排序，并提示用户哪份计划的哪些字段各自保留。
</details>
## 第五轮：工程化与交付｜常被问

### 发布证据

再讲发布证据。**一句话层。**

在确定的代码提交上生成软件包和文件清单，验证清单确实来自这次基线，再把待签名产物交给发布流程。签名私钥只在本机使用；发布端检查版本规则与文件指纹后切换线上清单。软件内更新曾出现下载到 100% 后仍失败：模态更新框挡住了发给登录窗或主界面的关闭消息，旧流程等不到 App 退出，随后回滚。**三句话层。**

更新相关工作要先用真打包程序走通旧版到新版；新程序必须报告版本正确且窗口可见、可响应，事务才写成 HEALTHY。测试替身可以验证分支，但窗口消息、进程退出和跨版本路径必须再用真打包程序验。**深一层。**

**你可以这样跟面试官说：**“构建、签名、发布和客户端替换是可分别核对的步骤。更新功能要从真实启动器走旧版到新版，并确认新窗口可见、能响应；自动测试、真包排练和用户本人验收各自回答不同问题。”

#### 常被问｜为什么下载完成或自动测试通过还不能算更新成功？

<details>

### 中断恢复

再说明恢复原则。**一句话层。**

数据库已经结算，课堂状态还在检测中，重试就重复结束同一次检测。操作前对照数据库，发现检测已经结束就补完收尾；给每道待答题一个固定编号，再次处理沿用原判定。**三句话层。**

测试特意停在两次保存之间，确认恢复后只结算一次；保存失败也必须报错，不能假装成功。**深一层。**

**你可以这样跟面试官说：**“一次检测在数据库结算后、课堂状态保存前中断，重试可能重复记账。恢复先查已经落库的事实，再补完收尾；固定编号保证重复请求沿用原判定。测试在两次保存之间中断，确认只结算一次。”
