# 设计取舍：为什么 MentorFlow 按这些规矩做

这篇按五个真实问题，讲清用户怎样定边界、系统因此作了什么取舍。面试优先级是本稿的学习判断，不是频率统计；每节标题只标一次优先级。只讲有明确记录的决定，不把工程师的猜测写成用户当时的理由。

事实核验基线：`e61fd00d`。

## 1. 题目要有资料证据，AI 不自由造题｜常被问

计分题要有资料里的证据。 **（一句话层）**

**历史背景：** 用户在 2026 年 10 月 3 日、6 日定下当时的题源边界：只用资料自带的题，不上网找题；资料没有题的模块只学不考。那一版流程允许 AI 在资料中定位并配对现成题，不允许自由编题，也不让 AI 判主观题。 后续的知识点结构增加了另一条有原文约束的路径，因此这段历史规则不能当成当前所有点的完整行为。

**当前做法：** 旧式知识点继续拆资料自带的原题；AI 按原文逐字拆出题干、答案或参考答案，程序核验字段确实来自原文并负责去重。新式 `concept_v1` 知识点先使用其小要点原文里已有的客观题；没有合适原题时，AI 定位小要点自己的原句和答案片段，也可从该小要点所关联的原文中提出带逐字出处的对照值。程序核验题干、答案和对照引用后组装候选题与选项，再让 AI 检查干扰项是否也被原文支持；程序验证返回的逐字证据、应用删除与最低数量规则，并据此决定候选能否入库。没有足够原文证据就丢弃候选，不自由编写题干、答案或无来源的干扰项。

客观题由程序按答案规则判分；资料问答题展示原文参考答案，学生对照要点自判。老师仍可用生活例子解释，但不能从比喻推出资料没有的事实；候选题是否入库、课堂怎样推进和怎样记分，都由程序规则控制。 **（三句话层）**

这像校长要求练习必须能指回讲义：老师可以帮忙找原题，也可以按讲义中的句子做一道有证据的填空；但不能凭空补出题目和答案。比喻的边界是，系统还会用程序核对原文片段，并让 AI 只检查干扰项是否也被原文支持；它不是让模型自行决定题目正确性。

**你可以这样跟面试官说：**“题目必须有采用资料里的证据。旧式知识点拆原题；新式知识点如果没有合适原题，AI 定位小要点原文里的句子和答案，也可从资料里找带出处的对照值；程序核验引用后组装候选题，AI 再检查干扰项是否也被原文支持。没有足够证据的候选会被丢弃；客观题由程序判，资料问答题由学生对照原文要点自判。”

复述这个取舍时，先把关键规则说完整：

旧式点从资料自带的原题中拆题；新式点先找小要点原文中的现成客观题，缺题时才定位可核验的原文句子与答案。 AI 可定位原句、答案和带原文出处的对照值；程序核对来源后组装候选，AI 检查干扰项的原文支持，程序再按逐字证据、删除和最低数量规则决定能否入库。 客观题由程序判分，资料问答题由学生先作答、再对照原文要点自判。

### 新旧两种知识点结构怎样保证题目有出处？

- 旧式点从资料自带的原题中拆题；新式点先找小要点原文中的现成客观题，缺题时才定位可核验的原文句子与答案。
- AI 可定位原句、答案和带原文出处的对照值；程序核对来源后组装候选，AI 检查干扰项的原文支持，程序再按逐字证据、删除和最低数量规则决定能否入库。
- 客观题由程序判分，资料问答题由学生先作答、再对照原文要点自判。
## 2. 模型请求从客户端直连，使用用户自己的 Key｜常被问

用户持钥，直接请求模型。 **（一句话层）**

**背景：** 产品要在课堂、计划和资料问答中调用模型，同时账号、同步和资料检索由自己的服务器处理。用户定下边界：模型继续由客户端直接请求，使用用户自己的 Key，不经 MentorFlow 服务器转发。

**决定：** 用户在桌面端配置模型连接，客户端按用途调用所选模型；凭据保存在本机操作系统的凭据库中。服务器承担账号和同步等业务，不能把模型调用顺手改成服务器代发。 **（三句话层）**

这项决定把模型调用和服务器业务拆成两条路径：客户端拿用户配置的 Key 与模型服务通信，服务器用 Java 处理账号、同步及资料检索。资料问答也沿用这个边界——Java 返回相关原文，客户端再把问题和片段交给用户选择的模型生成回答。当前项目状态列出七家模型厂商和两种中转站，但只验证过 DeepSeek；支持范围与验证范围不能混为一谈。 **（深一层）**

像自习室的学生自己选一位校外讲师并直接联系；校方负责教室、学籍和借书记录，不替学生把问题转交给讲师。这个比喻只表达请求路线，不代表模型凭据像普通聊天内容一样可随意保存或共享。凭据保存在本机操作系统的凭据库中，服务器不做模型请求中转；因此模型连接出错时要查客户端连接和模型厂商链路，账号同步或 RAG 检索故障则查对应服务器链路。

**你可以这样跟面试官说：**“模型由桌面端直接调用，用户在本机配置自己的 Key，服务器不代发模型请求。服务器处理账号和同步，RAG 服务器只把资料片段检索回来，最终回答仍由客户端交给用户选择的模型生成。”

复述这个取舍时，先把关键规则说完整：

用户定下边界：模型继续由客户端直接请求，使用用户自己的 Key，不经 MentorFlow 服务器转发。 凭据保存在本机操作系统的凭据库中。 Java 返回相关原文，客户端再把问题和片段交给用户选择的模型生成回答。

### 为什么模型 Key 不经过 MentorFlow 服务器？

- 用户定下边界：模型继续由客户端直接请求，使用用户自己的 Key，不经 MentorFlow 服务器转发。
- 凭据保存在本机操作系统的凭据库中。
- Java 返回相关原文，客户端再把问题和片段交给用户选择的模型生成回答。
## 3. 服务器适合的业务逐块迁到 Java，客户端与 AI 编排留在原位｜常被问

后端迁移，客户端先不动。 **（一句话层）**

**背景：** 项目当时的服务器是 Python，用户的求职方向是 Java + AI，两个项目都使用 Python。用户决定把服务器上适合 Java 的业务部分改写为 Java，同时尽量不影响现有服务；AI 提示词和编排继续用 Python，模型仍由客户端直连。

**决定：** 先迁资料目录，再迁同步，再迁账号；客户端不改，Java 与 Python 遵守同一 HTTP 契约。部署前做影子对比，代码按业务逐块迁移；服务器已于 2026 年 10 月 16 日整组切到 Java 并保留回退路径。 **（三句话层）**

边界不是“所有东西都改 Java”：模型调用不搬进服务器，桌面端不改，Keycloak 不动，静态软件更新也不属于这次迁移。RAG 是后来另行加入的服务器检索能力，记录里允许用 Java + LangChain4j 做，但不能据此声称 AI 提示词和生成也已经迁到 Java。服务器业务已于 2026 年 10 月 16 日正式切到 Java；用户登录、同步、上课的实测记录支持当前业务链已接通，注册、找回等发邮件流程仍未在线上真实走过。 **（深一层）**

像自习室把借书、收费和门禁这些后台账务逐项交给新系统，教室里学生用的桌面、老师讲课方式和校门身份系统先照旧；每换一项先和旧账对对，再分区启用，发现问题有回退路。比喻只说明迁移边界和顺序，不表示 Java 天然更快或更适合所有工作。结果是服务器后端业务当前由 Java 正式服务，客户端与 Python AI 编排各守原有职责。

**你可以这样跟面试官说：**“用户求职方向是 Java + AI，因此服务器适合 Java 的业务按块迁移，客户端不动，模型请求仍从客户端直连。Java 与 Python 遵守同一 HTTP 契约，服务器业务已整组切到 Java并保留回退；提示词和客户端编排继续用 Python。注册、找回等发邮件流程还没有线上实测。”

复述这个取舍时，先把关键规则说完整：

用户决定把服务器上适合 Java 的业务部分改写为 Java，同时尽量不影响现有服务；AI 提示词和编排继续用 Python，模型仍由客户端直连。 客户端不改，Java 与 Python 遵守同一 HTTP 契约。 部署前做影子对比；代码按业务逐块迁移，切换时整组上线并保留回退路径。

### 为什么没有把模型调用和所有客户端逻辑也迁到 Java？

- 用户决定把服务器上适合 Java 的业务部分改写为 Java，同时尽量不影响现有服务；AI 提示词和编排继续用 Python，模型仍由客户端直连。
- 客户端不改，Java 与 Python 遵守同一 HTTP 契约。
- 部署前做影子对比；代码按业务逐块迁移，切换时整组上线并保留回退路径。
## 4. 大知识点按主题分组，大小由主题决定｜偶尔问

主题连贯，内容不漏不重。 **（一句话层）**

**背景：** JavaGuide 计划里一个模块被机械地拆成许多小点，网关、配置中心、分布式事务等主题混在一起；标题有的只是列表项或“总结”，学习时很难知道正在讲什么。用户提出的不是“把点数削到某个固定数字”，而是让内容连贯、不要太碎。

**决定：** 知识点按主题重新分组，大小不设上下限，不机械追求每点相同；小要点、讲义和题保持不变，只调整大点分组与不清楚的标题。 **（三句话层）**

重分主题前，样本模块有 80 个大点、216 个小要点；模型提出主题分组和标题，程序检查每个小要点恰好归入一次。换入方案保留已经学过的点，并在副本上检查预演、换入、回滚、课堂和计划详情。当前记录显示第六模块从 80 个大点整理为 45 个，已经换入用户计划，但效果仍待用户查看；所以结果可以说“完成结构调整并保留内容”，不能说用户已验收学习体验。 **（深一层）**

像把自习室书架从“每个小标题占一格”改成按主题分区：网关相关材料放在一起，配置中心另设一组；每本书和里面的笔记不换，只调整归档位置和标签。这个比喻不代表软件只靠人工挪书，实际由模型提出分组、程序校验完整性，架构师在用户数据上执行换入。决定的后果是主题更集中、点数减少，但每个主题的大小可能不同，内容也没有因此自动变短。

**你可以这样跟面试官说：**“JavaGuide 计划按目录切得太碎，相关主题散在不同知识点里。用户决定按主题分组，不设大小上下限；小要点、讲义和题都保留，只改上层分组。程序校验每个小要点只归属一次，再在副本里验证换入和回滚。”

复述这个取舍时，先把关键规则说完整：

用户提出的不是“把点数削到某个固定数字”，而是让内容连贯、不要太碎。 小要点、讲义和题保持不变，只调整大点分组与不清楚的标题。 程序检查每个小要点恰好归入一次。

### 为什么知识点不按固定时长或数量切？

- 用户提出的不是“把点数削到某个固定数字”，而是让内容连贯、不要太碎。
- 小要点、讲义和题保持不变，只调整大点分组与不清楚的标题。
- 程序检查每个小要点恰好归入一次。
## 5. 本机把版本准备妥，再手动发布一个不可改写的版本｜偶尔问

本机验妥，再走发布链路。 **（一句话层）**

**背景：** 软件更新会替换用户正在使用的文件；如果发布前后版本内容变化，用户拿到的文件和版本清单就可能对不上。当前发布记录要求日常版本默认只发软件内更新文件和版本清单，不编安装程序；发布方式是 GitHub Actions 构建、本机签名、再发布。

**决定：** 发版前先在本机把候选版本验过，确认后再推送并触发一次 GitHub Actions 发布链；当前流水线由 GitHub Actions 构建、本机签名、再执行发布。签名在本机完成，签名私钥不交给 GitHub；发布出去的版本号不再改内容。 **（三句话层）**

GitHub Actions 手动触发构建，本机完成签名，再执行发布。日常更新默认不重新编安装器，给新用户或累计足够改动时才考虑编；用户端会验签、下载变更文件、替换程序并在中断时保留可恢复状态。版本差异是截至 2026 年 10 月 17 日的历史快照，不能当作长期当前版本；安装包和软件内更新是不同发布通道。 **（深一层）**

像自习室贴出一版已经盖章的课表：先在校内逐项核对，确认后再公开；公开后不把同一个版本号换成另一张课表。GitHub Actions 是构建流程的一环，签名在本机完成，发布步骤把签名后的内容送到更新站。比喻只表示先核对、签名和版本内容固定，不代表发布只靠一个按钮，也不表示当前每种安装场景都已由用户验收。后果是版本和签名可核对，日常只传变化文件；尚未走过的全新安装与注册不能借此说成已验收。

**你可以这样跟面试官说：**“发版按固定链路走：先在本机核对版本，再手动触发 GitHub Actions 构建；签名在本机完成，签名私钥不交给 GitHub，最后发布更新文件和清单。版本号一旦发出就不改内容，用户端会验签后再更新。”

复述这个取舍时，先把关键规则说完整：

发版前先在本机把候选版本验过，确认后再推送并触发一次 GitHub Actions 发布链。 GitHub Actions 手动触发构建，本机签名，再执行发布。 签名在本机完成，签名私钥不交给 GitHub；发布出去的版本号不再改内容。

### 为什么私钥留在本机，版本发布后不再改内容？

- 发版前先在本机把候选版本验过，确认后再推送并触发一次 GitHub Actions 发布链。
- GitHub Actions 手动触发构建，本机签名，再执行发布。
- 签名在本机完成，签名私钥不交给 GitHub；发布出去的版本号不再改内容。
## 学习路线：不用背清单

记住五个决定各自保护什么：AI 不越过资料和宿主规则，模型请求由客户端直连、不经 MentorFlow 服务器中转，Java 迁移按原接口分步走，知识点按主题组织，发布内容与签名保持可核对。版本号、工作流编号和每次发布的构建编号不用背；需要时从对应出处表和项目状态查。每个取舍都可以从背景讲起，再说明用户定了什么，最后讲它在系统里留下什么边界。
