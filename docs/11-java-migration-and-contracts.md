# 12｜Java迁移与兼容验证

## Q16｜迁移范围的选择｜必须能背

项目迁移不是为了给每项技术贴高低标签，而是按求职目标和业务职责划边界。用户的方向是 Java + AI；既有课堂流程、模型提示和编排已经在 Python，任务决定把适合展示 Java 的服务器目录、同步、账号业务逐块迁移，同时让模型仍由客户端用用户自己的 Key 直连，AI 编排继续留在 Python。这样是在既有产品结构里增加 Java 后端实践，不需要声称 Python 性能不足，也没有证据把它包装成微服务拆分需求。

比如用户登录后同步计划：桌面端仍按原协议发请求，Java 负责账号身份、同步接口和服务端保存；老师如何组织教学、何时判定完成仍由客户端原流程处理。边界按业务能力划分，已有课堂可以继续复用。用户明确选择 Java + AI 求职方向，所以可以坦然说明这是有意识的实践选择，而不是性能基准测试的结论。

**可以直接这样说：**“这个项目按 Java 加 AI 的求职方向做了业务分工。账号、目录和同步属于服务器业务，适合用 Java 实践；模型调用和 AI 课堂编排已经在 Python，就继续复用。它是按学习目标和职责划分，没有证据说 Python 性能不够，也不是为了拆微服务。”

### 为什么只把账号和同步等服务器业务迁到 Java？

- 用户求职方向是 Java + AI，因此需要在项目中实践 Java 后端。
- 目录、同步、账号是服务器业务；模型调用与 AI 编排按既定范围继续使用 Python 和客户端直连模型。
- 迁移依据是求职目标和职责边界，没有项目证据支持“Python 性能不够”或“必须微服务化”。

### 追问加练

面试官追问：“迁移后模型请求也改走 Java 吗？”答：“没有，模型继续由客户端使用用户自己的 Key 直连，AI 编排仍在 Python。”
## Q17｜后端兼容性验证｜讲清原理

兼容不是“服务能启动”或“返回了 HTTP 200”就算完成。客户端依赖的不只是成功状态码，还包括请求路径、字段、错误码、响应正文和认证行为；因此迁移要拿同一组 HTTP 契约请求分别打到旧实现和 Java 实现，再比较状态码、应用响应头、原始响应正文与关键数据库行。令牌、随机操作 ID、时间戳等动态字段要按规则归一化或检查格式，不能因此忽略其他差异。对关键业务还要让真实客户端代码经过实际代理拓扑走完整调用链，确认身份、会话和数据行为符合原约定。

例如，直接向后端发 HTTP 契约请求通过，并不能证明桌面端经由 HTTPS 边缘代理访问时也兼容。项目测试把真实的 `NativeCredentialClient`、`LoginSession`、`SyncTransport` 和 `ClosureClient` 放进代理拓扑，覆盖登录恢复、会话、同步和注销组合；这能发现只有真实客户端与代理一起运行才出现的协议差异。验证必须覆盖客户端实际依赖的链路，而不止单个后端端点。

兼容性还包括数据库演进和恢复边界。当前服务数据库迁移到 0045；旧 Python 容器虽停用保留，但迁移后的数据库并不因此自动回到旧结构。若恢复路径要求兼容新数据，必须按具体版本核验，不能承诺“旧服务随时无条件接管”。

**可以直接这样说：**“我会让同一组 HTTP 契约分别运行在旧、新后端，比较状态码、应用响应头、正文和数据库行；只对令牌、随机 ID、时间戳等动态值做明确归一化。再用真实客户端经实际代理拓扑走登录、会话、同步和注销流程。这样既核对协议，也核对持久化结果和真实调用链。”

### 怎样判断 Java 替代实现对原客户端兼容？

- 对旧、新服务运行同一组 HTTP 契约请求，比较状态码、应用响应头、正文与关键数据库行；仅归一化明确定义的动态字段。
- 让真实客户端类经过代理拓扑执行登录恢复、会话、同步和注销，验证完整调用链。
- 检查成功和认证失效、冲突、重试等失败场景；健康检查成功不等于客户端业务契约兼容。

### 追问加练

面试官追问：“健康接口是 200，就能确认客户端可用吗？”答：“不能，还要用真实客户端验证认证、代理和业务接口，并确认数据库结构兼容。”
