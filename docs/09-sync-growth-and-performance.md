# 10｜数据增长后的同步成本

## Q14｜同步成本的增量控制｜讲清原理

先分清两件事：本机课程库保存学习记录；同步只把需要跨设备共享的记录传到服务器。MentorFlow 不会每轮把整个数据库重新上传。客户端先按上次游标拉取之后的变化，再从本地待同步队列取尚未确认的记录。游标像书签，告诉系统上次读到哪；批量请求则像把多张变更单装进同一只信封，减少逐条往返。

举个例子：你今天新增了几十条学习记录，系统可以把它们分批提交，而不用重传以前已确认的计划和进度。服务端对每条记录核对版本；客户端收到确认后才把相应修改标成已上传。网络断开时，未确认的内容还在本机队列，下一轮可以继续处理。这里的“成本”指传输和处理的工作量；没有测量证据时，不把它说成固定时长或某个线上吞吐数字。

大批数据也可能碰到入口限额。批量请求若被服务器回 413，客户端会对半拆小后重试，成功的子批逐批确认；若单条仍过大，只把那一条留待重试，其余记录继续走。这个例子说明批量是效率手段，失败时仍需要可恢复的拆分策略，不能无限重复发同一个大包。

**可以直接这样说：**“数据变多后，我不会每次全量重传。客户端用游标只拉新增变化，再把本地待同步记录分批上传；成功的批次确认后就不再重复传。遇到请求过大，按 413 对半拆分，尽量让其他记录继续同步。具体耗时要以实际测量为准。”

### 记录变多后，系统怎样减少每轮同步工作？

- 游标记录已读取到的变化位置，因此客户端按增量读取，不必每轮重新拉全量历史。
- 本地待传记录每批最多100条合并上传并逐批确认，减少逐条请求的往返；未确认内容仍留队列待后续处理。
- 请求过大收到 413 时拆小批次继续，仍过大的单条留待重试，避免整批卡住。

### 追问加练

面试官追问：“如果某一条数据怎么拆都传不上去呢？”答：“拆到单条仍然过大时只留下这条待重试，其余记录继续同步。”
