# 模块07｜认证与授权：确认身份不等于开放所有数据

> **Q11｜深度：必须能背**

## 前置概念

**认证**回答“请求来自谁”。**授权**回答“这个身份在当前目标上可以做什么”。登录凭证通过校验，能让服务识别请求主体；具体请求仍要检查主体是否有当前组织、工作区或数据对象的权限。把两者混为一谈，就会把“你是这位用户”误说成“你能读取系统里任何用户的数据”。

## 自然讲解

可以把办公楼门禁想成两道检查：先看工牌是不是有效，再看这个人是否能进指定房间。工牌对应身份认证；房间名单和岗位范围对应授权。门禁确认你是员工，并不能推出你有权进财务档案室。这个比喻只解释两个问题的区别，不代表软件真的使用实体工牌。

在MentorFlow服务器里，受保护的API要求有已认证的Bearer身份。服务从凭证中取得签发方和主体，校验身份状态；普通用户请求还要带上所选组织，并由成员关系查询确认该用户在选定组织/工作区里仍是有效成员。成员关系不成立时，服务拒绝请求。认证这一步提供“谁在请求”的主体信息；组织、工作区成员关系才把请求限定到允许的业务范围。

授权还要落到具体数据访问上。比如资料问答服务从已认证的人类主体计算账号范围，检索在这个范围里进行；同步记录的查询和写入也把签发方、主体、组织、工作区一起作为范围条件。数据库行级安全策略可以作为隔离的纵深机制，但不能把责任含糊地推给数据库：入口和业务查询必须先把正确身份与目标范围带进去。

实际面试时，建议按“先认证、再授权、最后执行范围查询”回答。只说“用了Token”只说明系统有凭证，不足以说明服务怎样防止用户改一个资源ID就读到别人的记录。反过来，数据表做了隔离，也不表示业务层可以不检查请求主体。我们对账号隔离做过替身账号的接口核查，涵盖同步记录与资料检索；这说明已有实现和对应验证范围，不代表任何未来新增接口天然安全。

## 可直接口述

“认证是确认请求主体是谁，授权是判断这个主体能否访问当前组织、工作区和目标数据。MentorFlow服务器先验证Bearer身份并识别签发方和主体，再检查所选组织/工作区的有效成员关系；业务查询还按这个主体范围读写记录，RAG检索也按账号范围过滤。所以登录成功只是知道你是谁，不代表可以读取别人的计划或资料。”

### 认证和授权分别回答什么问题？

- 认证确认请求主体是谁，并取得可信的身份信息。
- 授权按当前主体与组织/工作区成员关系判断能否进行目标操作。
- 数据查询仍需使用正确账号范围；登录成功不等于能读取他人数据。

### 追问加练

追问：如果请求带了有效Token，但把资源ID改成别人的，应该靠什么挡住？

答法：服务端应依据已认证主体重新检查资源归属或查询范围，不能信任客户端给出的资源ID本身。
