# 模块09｜同步冲突与重试：CAS和幂等各管一类问题

> **Q13｜深度：必须能背**

## 前置概念

同步请求可能遇到两种麻烦。第一，另一台设备已经先改了同一条记录；第二，服务器其实已经写入成功，但回包在网络里丢了，客户端不知道成功与否。前者是并发写入冲突，后者是重复投递的不确定性。CAS（比较并交换）比较“我以为的版本”和当前版本；幂等键识别“这是不是之前已经处理过的同一请求”。两者都重要，但不互相替代。

## 自然讲解

想象两个人各拿着版本7的同一份讲义记录。甲先保存，服务器把版本改成8。乙仍拿版本7提交时，服务器发现“乙依据的版本已经过期”，就拒绝这次覆盖并返回版本冲突。这个比较当前revision是否等于expected_revision、相同才写成下一版，就是CAS在这里的作用：防止旧状态悄悄盖掉新状态。它回答“现在允许不允许写”，不负责辨认网络重试是不是同一个请求。

再看回包丢失：客户端用expected_revision=7提交，服务器成功写出revision=8，但响应没回到客户端。客户端若换一个全新的请求身份再提交，服务器会看到当前版本已是8，正确地报冲突；然而客户端仍不知道先前那次是否成功，体验上就像“提交结果不确定”。所以客户端会为同一份待提交内容生成稳定的request_id，重试时保持相同；服务端按账号范围查已处理回执，同一个request_id和相同请求摘要会直接返回先前响应，不再重复写入。若同一键却带了不同内容，服务端拒绝，避免把两件事误认成一件。

这就是边界：CAS保护数据的新旧顺序，幂等性保护请求重复送达时的结果一致。只有CAS、没有幂等，重复请求在第一次已经成功但回包丢失时会变成版本冲突；只有幂等、没有CAS，两台设备各用不同request_id并发写同一旧版本，仍可能互相覆盖。两者组合后，旧版本竞争被拒绝；同一个已成功请求重试则拿回原回执。它不替用户自动合并冲突，冲突如何重读和合并是客户端后续流程。

## 可直接口述

“CAS管并发版本：请求带上我读到的expected_revision，只有它仍等于服务器当前revision才写入下一版，否则拒绝，防止旧数据覆盖新数据。幂等键管重复请求：同一request_id和同一内容再送达时，服务器返回之前保存的响应，不重复写；同一个键换了内容则拒绝。一个解决版本竞争，一个解决响应丢失后的安全重试，不能互相替代。”

### 同步里的CAS与幂等请求分别解决什么问题？

- CAS比较expected_revision和当前版本，只允许基于最新版本写入，防止并发旧写覆盖。
- 幂等request_id识别同一逻辑请求的重试，成功后重放会返回已存响应。
- CAS管版本竞争，幂等管重复送达；不同请求仍可能冲突，同一键换内容会被拒绝。

### 追问加练

追问：只有CAS为什么不能处理回包丢失？

答法：首次写入成功后版本已前进，换新请求重试会被当成过期版本；稳定request_id才能让服务端返回原回执。
